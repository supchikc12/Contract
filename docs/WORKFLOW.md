# Contract — как работать вдвоём

Практический протокол для двух разработчиков в одном Unity-проекте. Цель — не «не мешать
друг другу», а **интегрироваться каждый день и не терять работу**. Git настроен, но часть
защиты ещё не включена (см. раздел 3.4 и `scripts/setup-git-merge.ps1`).

Правила коротко:

1. `main` всегда рабочая; прямых пушей в неё нет.
2. Ветка живёт ≤ 3 дней; вливаешь маленькими кусками.
3. Каждый день — `pull main` утром и `push` своей ветки вечером.
4. Один файл — один владелец; чужие скрипты не правим без явного «ок».
5. Сцена/префаб — только по одному человеку за раз, по договорённости в чате.
6. Общие типы (`ItemData`, `ItemState`, `InventoryManager`, интерфейсы) меняем отдельным PR.
7. Перед PR — ребейз на `main`, открыть Unity, консоль чистая, смоук-тест.
8. Мержит автор после ревью, squash; ветку удаляем.
9. `Library/`, `Temp/`, `Logs/`, `UserSettings/`, `*.csproj`, `*.sln` — не коммитим.
10. Владелец системы — не навсегда; отпуск/болезнь → передача через `docs/CODE.md`.

Заполните колонку «Владелец» (A / B). Пока не заполнено — считаем, что владелец тот,
кто последним вливал изменения в этот модуль.

| Зона | Файлы / объекты | Владелец |
|---|---|---|

| Items | `ItemData.cs`, `ItemState.cs`, `ItemInstance.cs`, `ItemGridPlacement.cs`, `ItemView.cs`, `ItemCategory.cs` | |
| Equipment | `EquipmentSlot.cs`, `EquipmentSlotData.cs`, `EquipmentSlotsManager.cs` | |

| Scenes | `Assets/Scenes/**` | |
| Prefabs / UI-префабы | `Assets/Prefabs/**` | |

| Build / ProjectSettings / Packages | `ProjectSettings/**`, `Packages/**` | |
| Docs | `docs/**`, `AGENTS.md` | оба |

Правила владения:

- «Не трогать чужие скрипты» — правильно, но мало. Владелец отвечает за **систему**, а не за файл:
  правки в его зоне делает он, либо вы согласуете их в чате заранее.
- Чужой код можно **читать** всегда — `docs/CODE.md` для этого и написан.
- Критический баг в чужой зоне: пишешь владельцу, он чинит. Если владелец недоступен —
  фикс делаешь сам, но отдельным PR с пометкой `hotfix` и ревью владельца постфактум.
- Нельзя «тихо» переименовывать публичные методы/поля: это ломает сцены и код напарника.

## 2. Git-модель

### 2.1 Ветки

```
main                  — всегда рабочая, защищена
feat/<scope>-<тема>   — новая функциональность
fix/<scope>-<тема>    — багфикс
refactor/<scope>-<тема> — рефакторинг без изменения поведения
docs/<тема>           — документация
```

`scope` — из списка: `player`, `inventory`, `items`, `equipment`, `ui`, `menu`, `editor`,
`assets`, `scenes`, `build`, `docs`.

Примеры: `feat/inventory-split-stack`, `fix/equipment-slot-drag`, `refactor/items-view`.

Правила:

- ветка от свежей `main`, живёт не дольше 3 дней;
- одна ветка — одна тема; не мешаем фикс и рефакторинг;
- если тема не влезает в 3 дня — дели на этапы и вливай по частям.

### 2.2 Старт работы

```bash
git switch main
git pull --ff-only
git switch -c feat/inventory-split-stack
```

### 2.3 Коммиты

Формат: `тип(область): короткое описание` — **только на русском языке**, заголовок и тело.
Типы: `функционал`, `исправление`, `рефакторинг`, `документация`, `хозяйство`.

```
функционал(инвентарь): разделение стака по ПКМ
исправление(экипировка): слот не очищался после выброса
рефакторинг(предметы): вынес поворот сетки в отдельный метод
документация(код): справочник по скриптам
хозяйство(сборка): обновил packages-lock
```

- один коммит — одно логическое изменение;
- не смешивай форматирование и логику;
- сообщение отвечает на «что и зачем», а не «какие файлы».

### 2.4 Перед PR

```bash
git fetch origin
git rebase origin/main
# открыть Unity, дождаться импорта, проверить консоль и смоук-тест
git push -u origin HEAD
```

Если ветку уже кто-то смотрел — вместо rebase делай `merge origin/main`, чтобы не ломать ревью.

### 2.5 PR и мерж

- PR открывается сразу, как начал работу (draft), — это и есть «заявка на занятость».
- Ревьюер — второй разработчик. Свой PR не мержим без ревью.
- Размер: до ~300 строк кода; больше — дроби.
- В описании: что, зачем, как проверил, какие общие контракты затронуты, скриншоты для UI.
- Мерж — **squash**, ветку удалить.
- `main` защищаем в GitHub: require PR, require review, запрет force-push.

Шаблон описания уже лежит в `.github/PULL_REQUEST_TEMPLATE.md`.

## 3. Unity-специфика

### 3.1 Версия и пакеты

- Оба работают на **одной** версии редактора: другая версия — другой формат сцен и импортёров.
- **Сейчас версии расходятся:** в `ProjectSettings/ProjectVersion.txt` зафиксирована **6000.0.22f1**,
  а проект открывался в **6000.6.8f1**. После открытия новее Unity сама переписала
  `ProjectSettings/**`, `Packages/manifest.json`, `packages-lock.json` и часть `.meta`
  (TextureImporter serializedVersion 12 → 13). Это ещё не закоммичено.
- Решение принимается вдвоём: либо оба ставят 6000.0.22f1 и откатывают эти диффы,
  либо один делает PR `chore(build): upgrade to 6000.6.8f1`, второй обновляет редактор
  и проверяет проект после мержа.
- Пока версии не совпали — **не коммитить** изменения `ProjectSettings/**`, `Packages/**`
  и `.meta`, которые Unity сделала сама при открытии.
- `Packages/packages-lock.json` коммитится. Обновление пакетов — отдельный PR и сообщение в чат.
- `ProjectSettings/**` — общая зона: меняем по одному, маленькими коммитами, с описанием.

### 3.2 Мета-файлы и GUID

- Любое перемещение/переименование ассетов — **только внутри Unity**.
- `.meta` коммитится вместе с ассетом, всегда.
- Не копируй `.meta` между машинами и не создавай вручную: GUID должен быть один.
- Конфликт `.meta` — не мержим: оставляем GUID, на который ссылаются сцены/префабы,
  второй файл удаляем, ассет переимпортируем.

### 3.3 Сцены и префабы

Сцены и префабы — YAML, но нормально руками не мержатся.

- `Assets/Scenes/MainWorld/SampleScene.unity` — одна сцена, один редактор за раз.
- Эксперименты — в отдельных сценах (`Assets/Scenes/Dev/<ник>/...`), в build не добавлять.
- Префабы правим в Prefab Mode, а не на экземплярах в сцене.
- Если оба должны править один префаб — разносим на вложенные префабы или делим по времени.
- Перед правкой сцены — сообщение в чат: «беру SampleScene на 30 минут».

### 3.4 SmartMerge (UnityYAMLMerge)

Сейчас в репозитории **нет** `.gitattributes` и не настроен merge-драйвер, поэтому конфликты
`.unity`/`.prefab` решаются вручную. Исправляется один раз на машину:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\setup-git-merge.ps1
```

Скрипт пропишет локальный git-конфиг на `UnityYAMLMerge.exe` из `E:\project\unt\6000.6.8f1`.
Файл `.gitattributes` уже добавлен в репозиторий — его нужно закоммитить, чтобы правило
действовало у обоих.

SmartMerge помогает, но **не гарантирует** корректный результат: после мержа сцены
обязательно открыть её в Unity и проверить.

### 3.5 Ассеты

- Бинарные файлы (PSD, FBX, аудио) одновременно не редактируем.
- Большие файлы: Git LFS установлен, но включать его нужно осознанно — это отдельная миграция
  истории (`git lfs migrate import`), делать её в спокойный день, не в середине спринта.
- Импорт-настройки (текстуры, модели) — часть ассета; меняешь — проверь, что не сломал вид у напарника.

## 4. Протокол «занято»

Git не блокирует файлы, поэтому занятость объявляем явно.

1. Перед началом: сообщение в чат — «беру `InventoryManager`, чиню стаки, ветка `fix/inventory-stack`».
2. Сразу открываешь draft PR — это вторая, формальная метка занятости.
3. Закончил/влил — пишешь «освободил», PR закрыт/смержен.
4. Если нужно тронуть чужую зону — сначала «ок» владельца, потом работа.
5. Если работа встала — снимаешь draft или помечаешь «на паузе», чтобы не держать зону.

Долгие задачи (сцена, большой рефакторинг) — объявляются на утреннем синке.

## 5. Общие контракты

Эти файлы используют оба, поэтому меняются только по согласованию:

| Контракт | Что определяет | Кто ломает чаще всего |
|---|---|---|
| `ItemData`, `ItemCategory` | данные предмета, категории | добавление полей/категорий |
| `ItemState`, `ItemStateData` | runtime-состояние, снимки | смена состава данных, сериализация |
| `InventoryManager` (public API) | drag, стаки, контейнеры, выброс | новые публичные методы, смена сигнатур |
| `ItemInstance` (public API) | размещение, поворот | смена сигнатур `CanPlaceInGrid`/`PlaceInGrid` |
| `InitializeGrid`, `InventoryGrid` | сетки и фильтры | смена смысла `gridSize`, `isContainerGrid` |
| `IItemAction`, `IInventoryClickHandler` | расширение меню/кликов | добавление методов в интерфейс |
| Имена в UI-префабах | `Conteyner`, `Header/Button_Close`, `Grid`, `Viewport` | переименование ломает код |

Правило изменения контракта:

1. Отдельный PR `refactor(contract): ...` или `feat(contract): ...`.
2. В описании — что меняется и что должен сделать напарник.
3. Сначала обновляется код и `docs/CODE.md`, потом сцены/префабы.
4. Если ломается API — добавляем совместимую обёртку на один релиз, а не «сразу выпиливаем».

## 6. Ежедневный цикл

**Утро (5 минут):**

1. `git switch main && git pull --ff-only`.
2. Открыть Unity, дождаться импорта, проверить консоль.
3. Синк в чате: кто что берёт, кто трогает сцены/префабы.

**В течение дня:**

- Ветка от `main`, маленькие коммиты, пуш хотя бы раз в пару часов.
- Перед правкой сцены/префаба — сообщение.
- Раз в день — `git fetch && git rebase origin/main` в своей ветке.

**Вечер (5 минут):**

1. `git push` даже если не готово (draft PR).
2. Сообщение: что сделано, что осталось, что занято завтра.
3. Если `main` сломан — сразу чиним, не ждём утра.

**Раз в неделю (30 минут):**

- пройтись по `docs/CODE.md`, обновить устаревшее;
- посмотреть открытые TODO/заглушки;
- договориться о следующем куске работы и владельцах.

## 7. Чек-листы

### Перед началом работы

- [ ] `main` обновлён, проект открывается без ошибок.
- [ ] Ветка создана от свежей `main`.
- [ ] Зона не занята напарником.
- [ ] Понятно, какие общие контракты могут быть затронуты.

### Перед PR

- [ ] `git rebase origin/main` выполнен.
- [ ] Unity открыт, консоль без `error CS`.
- [ ] Смоук-тест: сцена грузится, инвентарь открывается, предмет тащится, ПКМ-меню работает.
- [ ] Нет случайных изменений в чужих зонах (`git diff --stat`).
- [ ] Нет `Library/`, `Temp/`, `Logs/`, `*.csproj`, `*.sln`.
- [ ] Обновлён `docs/CODE.md`, если менялись публичные API.

### После мержа

- [ ] `main` подтянут, Unity переимпортировал, консоль чистая.
- [ ] Сцена и префабы открываются, ссылки не потеряны.
- [ ] Напарник предупреждён о мерже и возможном ребейзе.

## 8. Конфликты — что делать

| Конфликт | Действие |
|---|---|
| `.cs` | Резолвить руками, сохранить обе логики, собрать проект, прогнать смоук-тест |
| `.unity` / `.prefab` | Не мержить руками. Взять одну сторону целиком, вторую переиграть в Unity. SmartMerge — только как подсказка |
| `.asset` (ScriptableObject) | Обычно взять одну сторону; если оба добавляли поля — свести вручную и проверить в инспекторе |
| `.meta` | Оставить GUID, на который ссылаются ассеты; дубликат удалить, ассет переимпортировать |
| `ProjectSettings/*` | Взять одну сторону, настройки переприменить через UI |
| `packages-lock.json` | Взять версию из `main`, обновление пакетов — отдельным PR |

Если конфликт большой и непонятный:

```bash
git merge --abort        # или git rebase --abort
git switch main && git pull
git switch -c fix/<тема>-2   # пересобрать изменение заново маленькими кусками
```

Потерянную работу ищем через `git reflog` и `git fsck --lost-found`.

## 9. Анти-паттерны

- Держать работу неделю локально и потом «вливать всё».
- Править чужой скрипт «по-быстрому», не сказав.
- Мержить сцену руками в текстовом редакторе.
- Коммитить `Library/`, `Temp/`, `Logs/`, `UserSettings/`.
- Обновлять Unity или пакеты в одиночку.
- Делать force-push в `main` или в чужую ветку.
- Смешивать рефакторинг, фикс и новую фичу в одном PR.
- Копировать `.meta` и ассеты через проводник.
- Оставлять `main` сломанной «до вечера».
- Молчать о занятости сцены/префаба.

## 10. Быстрый старт для второго разработчика

```powershell
git clone https://github.com/supchikc12/Contract.git
cd Contract
powershell -ExecutionPolicy Bypass -File .\scripts\setup-git-merge.ps1
# открыть проект в Unity Hub на согласованной версии редактора (см. раздел 3.1)
```

Дальше — цикл из раздела 6: ветка → маленькие коммиты → draft PR → ревью → squash-мерж.
